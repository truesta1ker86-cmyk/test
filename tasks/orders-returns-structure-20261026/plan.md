# План: разделить страницы заказов и возвратов

Дата: 26 октября 2026. Область: Angular V2, репозиторий `test/`.
Первоначальный запрос — составить план. После поручения пользователя план реализован локально; результаты приведены в verification.md.

## Как поняты требования

- У заказов и возвратов должны быть отдельные компоненты страниц.
- Модуль страницы находится непосредственно в `pages/orders/` или `pages/returns/`.
- Компоненты внутри этих страниц не получают собственных NgModule: их объявления и зависимости собираются в модуле страницы.
- Переиспользуемый фильтр находится в `shared/data-table-filter/`, по аналогии с `shared/data-table/`. Модуль общего фильтра остаётся на верхнем уровне этой shared-папки.
- Сохраняются компоненты работодателя, действующие API-контракты и поведение страниц.

## Что обнаружено

- `pages/orders/orders.module.ts` импортирует вложенный `OrdersPageModule`.
- `pages/returns/returns.module.ts` также использует `OrdersComponent`; выбор страницы определяется через `entity`.
- В `orders/components/` есть отдельные модули списка, фильтра, массовых действий и деталей.
- `shared/data-table-filter/data-table-filter.module.ts` уже существует и экспортирует фильтр столбцов. Его нужно расширить, сохранив текущих потребителей.
- В существующем shared-фильтре есть незакоммиченная правка пользователя; при реализации её необходимо сохранить.

## Шаги

### 1. Подготовить общий фильтр

Перенести переиспользуемую часть `OrderFilterComponent` в отдельный компонент внутри `shared/data-table-filter/components/`. Объявить и экспортировать его через существующий `DataTableFilterModule`. Настройки и значения фильтра передавать из страниц; shared-код не должен импортировать типы и стили из `pages/orders/`.

Приёмка: общий фильтр доступен через один shared-модуль; существующий фильтр столбцов продолжает работать. Проверка: профильные тесты общего фильтра и проверка архитектуры.

Зависимости: нет. Область: новый компонент и его зависимости, существующий shared-модуль; перенос разбить на небольшие патчи.

### 2. Создать самостоятельную страницу возвратов

Добавить `ReturnsComponent` со своим шаблоном и состоянием. Зарегистрировать его непосредственно в `ReturnsModule`. Маршрут возвратов должен открывать этот компонент. Для таблицы и общего фильтра использовать shared-компоненты.

Приёмка: возвраты открываются отдельной страницей, не требуют `OrdersComponent`; загрузка, поиск, фильтрация, пагинация и экспорт сохраняются. Проверка: профильные тесты страницы и сценарий возвратов в браузере.

Зависимости: шаг 1. Область: модуль возвратов, TS/HTML/CSS нового компонента и его тесты.

### 3. Оставить OrdersComponent только для заказов

Убрать из страницы заказов ветвления, обслуживающие возвраты. Сохранить текущие/завершённые заказы, фильтры, выбор строк, детали, массовые действия и экспорт.

Приёмка: заказы работают отдельно; на странице отсутствует переключение между сущностями orders/returns. Проверка: профильные тесты и браузерные сценарии заказов.

Зависимости: шаг 2. Область: компонент заказов, его шаблон и непосредственно затронутые проверки.

### 4. Собрать основную структуру OrdersModule на уровне страницы

Перенести объявления OrdersComponent, списка заказов и массовых действий в `pages/orders/orders.module.ts`. Удалить ставшие ненужными вложенные `OrdersPageModule`, `OrderListModule`, `OrderBulkActionsModule`, обновить импорты.

Приёмка: эти компоненты объявлены ровно в одном модуле; основной модуль страницы содержит необходимые зависимости. Проверка: сборка Angular и проверки архитектуры.

Зависимости: шаг 3. Область: основной модуль заказов и три вложенных модуля; при необходимости связанные импорты править отдельным патчем.

### 5. Завершить перенос деталей и фильтра

Объявить компонент деталей в основном модуле страницы заказов и убрать его вложенный модуль. Подключить общий фильтр через DataTableFilterModule, затем удалить старую локальную реализацию фильтра и её модуль после проверки всех ссылок.

Приёмка: в компонентах Orders/Returns нет собственных NgModule; общий фильтр доступен из shared, детали заказа открываются. Проверка: поиск старых импортов, сборка и профильные тесты. Перенос деталей и удаление старого фильтра выполнить отдельными небольшими патчами.

Зависимости: шаги 1 и 4. Область: модуль заказов, модуль деталей и прежняя папка order-filter.

### 6. Проверить итоговое поведение

Запустить подходящие проверки из package.json: профильные тесты, `architecture:check`, `employer:check`, `filters:check`, сборку. В браузере проверить прямой переход на обе страницы, фильтры и их сброс, параметры URL, сортировку, пагинацию и экспорт. На заказах дополнительно проверить детали и массовые действия в разрешённом локальном сценарии.

Приёмка: страницы независимы, структура модулей соответствует требованиям, прежнее поведение сохранено. Перед браузерной проверкой явно выбрать источник API: текущий proxy направлен на серверный API.

Зависимости: шаги 1–5. Область: проверки изменённых сценариев; backend и публикация не входят в этот план.

## Контрольные точки

1. После шагов 1–2: общий фильтр и отдельная страница возвратов собираются и проходят профильные проверки.
2. После шагов 3–5: нет устаревших ссылок и повторных объявлений компонентов, модули страниц собраны на уровне pages.
3. После шага 6: зафиксированы результаты автоматических и браузерных проверок.

## Риски

- При переносе объявлений нельзя объявить один Angular-компонент в двух модулях.
- Общий фильтр должен сохранить поведение фильтра столбцов и не получить зависимости от страниц.
- Нужно сохранить URL-параметры, серверные column_filters и изоляцию магазинов.
- Накопленные изменения пользователя не удалять и не включать в задачу автоматически.

При составлении первоначального плана тесты и сборка не запускались. После реализации результаты записаны в [verification.md](verification.md).

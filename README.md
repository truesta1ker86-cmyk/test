# Ozon × 1С — Angular

Новый интерфейс сервиса на Angular 22.2.2 и TypeScript 6. Основа — исходный `test/master` работодателя (`8d9f71e7551ac5c51352c4a3b33876fc109febdd`). Перенос бизнес-логики находится в ветке `ii_test`. Общие компоненты взяты из этой основы: DataTable на PrimeNG, FilterService и элементы фильтров, Page, PageAttach, Navigation и спрайт иконок.

## Что перенесено

Каталог товаров, карточки и сопоставление с 1С, остатки и распределение по складам, расчёт цен и формулы, финансовые представления и выгрузки, заказы и возвраты, акции, профили магазинов и настройки. Общие таблицы используют компактный шрифт, фильтры заголовков, подсветку строк и карточку товара при наведении.

Это исходники фронтенда. Прежний Python-бэкенд и отдельный C++-сервер находятся в основном проекте и сюда не скопированы. Данные не встроены в приложение: для работы разделов нужен совместимый API на `/v2/api/`. Наличие экрана не означает, что все его действия уже проверены с сервером.

## Запуск

Требуется Node.js 24.15+ в ветке 24; проверенная версия указана в `.nvmrc`.

```sh
npm ci
npm start
```

Интерфейс открывается по адресу `http://127.0.0.1:4200/`.
Актуальный `proxy.conf.json` Виталия направляет `/v2/api/*` в
`https://pujer.ru/api/*`, передавая Origin этого V2 и проверяя TLS-сертификат.
Для входа нужен отдельный ключ, переданный владельцем; его не записывают в
исходники. Это подключение к существующему V2, а не автоматический запуск
локальной копии базы. Документация API: `npm run api:docs` →
`http://127.0.0.1:55354/`; ограничения профиля см. в
[development-api/README.md](development-api/README.md).

## Сборка и проверки

```sh
npm test
npm run build
npm run format:check
npm run architecture:check
npm run employer:check
npm run filters:check
```

Сборка находится в `dist/ozon1c-v2/browser/`; base href — `/`. Веб-сервер должен отдавать `index.html` для глубоких ссылок и отдельно маршрутизировать `/v2/api/*` к совместимому API. При публикации под префиксом его задают явно на этапе сборки.

## Проверка с копией базы

Отдельный Docker-контур на машине разработчика доступен по адресу `http://127.0.0.1:55349/v2/products`. Он разворачивается из основного проекта и содержит собственную копию PostgreSQL, API и Angular. Базы, дампы, ключи и рабочие настройки в этот репозиторий не включены.

Изоляция обеспечивается сервером: автоматические синхронизации, отправки и внешние вызовы в копии отключены, разрешены только явно перечисленные локальные действия. Один фронтенд этих ограничений не обеспечивает. Не направляйте его на рабочий сервис для проверки записей. Для работы с готовым Docker-контуром используйте его адрес напрямую: API копии проверяет исходный Origin.

## Структура и модули

До переноса на структуру образца несколько компонентов лежали рядом в общих
папках, например `finance/finance-page.ts`, `finance/profit-summary.ts`,
`finance/report-table.ts`. Типы, интерфейсы и настройки часто объявлялись в тех же
файлах. Компоненты подключались как standalone.

Теперь каждый компонент находится в своей папке: например,
`pages/profit/components/finance-page/`. В ней лежат исходник компонента, шаблон,
стили, тесты и NgModule; вспомогательный код разнесён по `infrastructure/`.
Общие компоненты таблиц и фильтров используются из исходного образца.
Бизнес-операции Ozon × 1С сохраняются в адаптерах разделов и существующем API.

- `src/app/app.module.ts`, `app-routing.module.ts` — запуск и загрузка модулей разделов.
- `src/app/pages/{products,mapping,stocks,pricing,profit,orders,returns,push,team,imports,overview}` — разделы в структуре исходного проекта. URL v2 сохранены: например, `/finance` загружает `ProfitModule`, `/promotions` — `PushModule`, `/account` — `TeamModule`.
- `components/<component>/` — отдельная папка каждого компонента с шаблоном, стилями, тестами и объявляющим NgModule. Все производственные компоненты используют `standalone: false` и `ChangeDetectionStrategy.OnPush`.
- `infrastructure/services`, `constants`, `types`, `interfaces`, `utils` — сервисы, конфигурации, типы, интерфейсы и функции соответствующего раздела или компонента.
- `src/app/core/infrastructure` — HTTP, сессия и защита контекста магазина.
- `src/app/shared` — исходные общие механизмы работодателя и дополнения интерфейса v1.
- `DESIGN.md` — правила интерфейса.

Сервисы одного компонента объявляются в его `providers`. Это относится к `CardLocalDrafts`, `CardDrafts`, `MappingDrafts`, `LocalStockAutomation`, `PricingSelection`, `PromotionDrafts`, `StocksApi`, а также к экземпляру `ProgressService` внутри `ProgressComponent`. Исходный `SseModule.forRoot` сохраняет свой публичный контракт. Общие для нескольких компонентов магазино-зависимые хранилища сохраняют отдельные состояния по tenant id. `FilterService` в диалогах столбцов и многозначных отборах создаётся отдельно для каждого экземпляра компонента.

DataTable получает данные и конфигурации колонок через исходный API; специфическое отображение использует предусмотренные `headerTemplate` и `cellTemplate`. Финансовое дерево преобразуется в видимые строки в финансовом компоненте, а расчёты остаются в соответствующих разделах. Самодельной таблицы с селектором `table[appDataTable]` больше нет.

Стили таблиц остатков, распределения, импортов, настроек и финансов подключены
в компонентах этих разделов. Общая DataTable не содержит селекторов страниц и
правил финансовых ячеек. Спрайт проверяется через `IconsSpriteModule`: создание
компонента и наличие всех 26 исходных SVG-символов с геометрией.

`architecture:check` проверяет модульное объявление, OnPush, размещение компонентов, сервисов, типов и интерфейсов, а также существование шаблонов и стилей. В `vitest.config.mjs` отключён дисковый кэш модулей: Angular передаёт Vitest собранные виртуальные модули, и проверка должна учитывать изменения импортированных исходников. [Описание кэша Vitest](https://vitest.dev/config/fsmodulecache).

Используется PrimeNG 22 из исходного набора зависимостей. В актуальном `ii_test` Виталий отключил провайдер темы Aura; оформление контролов задаёт проектный `shared/ui/styles/controls.css`, подключённый под `body.o1c-ui`. Код проверки лицензии не изменяется, ключ лицензии в репозиторий не добавляется. Отключение темы само по себе не меняет условия использования зависимости.

Сессия хранится в HttpOnly-cookie. Секреты и production-конфигурация в клиентский код не добавляются.

## Сверка с исходным репозиторием работодателя

`npm run employer:check` сравнивает `shared` с точным исходным коммитом работодателя. Проверяются все 53 класса, все 197 методов, их имена и сигнатуры, сохранение исходных полей и использование исходных элементов фильтров в адаптерах v2. Два одноимённых `PendingTracker` сопоставляются по своим подсистемам.

185 тел методов совпадают по синтаксическому дереву. Форматирование, кавычки и лишние скобки не учитываются, содержимое строк учитывается. 12 методов адаптированы для OnPush, URL v2, сохранения фокуса, сброса и зависимостей фильтров и интеграции Angular Forms. Добавлены 7 методов `DataTableComponent` для источника страниц и обновления, `PageComponent.closeMenu` и 7 методов `FilterBaseComponent` для ControlValueAccessor и синхронизации конфигураций. Поля `PageComponent.currentTitle` и `currentSubtitle` преобразованы в getter для строковых и Signal-заголовков. Каждое отличие с причиной и контрольной суммой записано в `scripts/employer-method-adaptations.json`; недокументированное изменение приводит к ошибке проверки.

Дополнительно учтено вычисляемое поле `FilterService.validValues`: отключённые зависимые фильтры не считаются активными. Значения констант при их переносе в `infrastructure/constants` сохраняются; проверка отличает такие переносы от изменения вычисления.

Это проверка API исходной общей основы, а не побайтового совпадения всего фронтенда с демонстрационным приложением. Бизнес-страницы и запросы Ozon × 1С остаются в разделах сервиса.

Архитектурная проверка также находит статические конфигурации внутри классов, включая `as const` и spread констант. Для сервиса единственного компонента проверяются локальный provider и отсутствие `providedIn: root`.

## Фильтры разделов и исходные компоненты заказов и остатков

Все поля отбора используют исходные `app-filter-*` и локальный `FilterService`. Бизнес-формы связаны с ними стандартным `ControlValueAccessor`; преобразование JSON-массивов API выполняет чистый `filterValues` pipe, чтобы неизменённый отбор не создавал цикл NgModel. Исходные шаблоны PrimeNG остаются местом отображения контролов. Собственный `StockChoiceFilter` удалён. Варианты фильтров цен загружаются из существующего `/pricing/filter-values`: `/pricing/refs` не содержит полного набора вариантов. Схемы FBS/FBO/RFBS берутся из того же набора значений, что и редактор; план минималки и API-маржа остаются отдельными полями.

Заказы разделены на `OrdersComponent`, `OrderFilterComponent`, `OrderBulkActionsComponent` и `OrderListComponent` по образцу исходного проекта; возвраты используют тот же список с собственным контрактом API. В остатках подключены `InventoryFilterComponent`, исходные `InventoryReconciliationComponent`, `InventoryDetailComponent` и `WarehousePickerComponent`; матрица находится в `allocation/allocation-matrix`. Проверки готовности FBS, скрытого выбора, ограничений складов и актуальности черновиков сохранены. Эндпоинты и бизнес-расчёты не заменяются демонстрационными запросами.

`npm run filters:check` проверяет все шаблоны разделов, включая группы switch: 86 деклараций исходных контролов, локальные providers, отсутствие самодельных таблиц и нативных полей в панелях отбора, подключение компонентов заказов и остатков. 52 декларации `app-data-table` сохранены. Поля редактирования цен, правил, карточек и настроек остаются бизнес-формами.

В тестовой копии подключены `/pricing/views` и `/pricing/column-values`. Расширение находится в `sandbox_backend`; основной сервер не изменяется. Отборы сохраняются в PostgreSQL отдельно для каждого магазина; доступны создание, обновление, удаление и один отбор по умолчанию. Читать варианты может сотрудник с правом просмотра, сохранять отборы — владелец или менеджер.

Значения столбца собираются по всему текущему отбору, независимо от страницы. Собственное условие столбца при загрузке вариантов исключается, остальные условия сохраняются. Диапазоны, текст, выбранные значения, пустые ячейки и проценты используют те же данные, что отображаются в таблице. `/pricing/configs` и выбор товаров для массовых действий используют один серверный отбор. Расчёты берутся из существующих `pricing.list_configs` и `CalcEngine`; формулы не дублируются. План минималки и схема маржи API остаются независимыми.

Подключение, проверки и откат тестового API описаны в [sandbox_backend/README.md](sandbox_backend/README.md). Проверены реальные HTTP-запросы, конкурентная смена отбора по умолчанию, границы магазинов и браузерное сохранение/обновление/восстановление после перезапуска API. Фильтр цены проверен применением диапазона к реальной строке.

Браузерный проход 18.10.2026 дополнительно исправил отборы и общий сброс заказов,
постоянную догрузку цен из-за вложенного ограничения высоты, регистрацию фильтра
характеристик в форме карточки и применение финансовых столбцовых условий.
Это историческая проверка прежнего режима полной загрузки заказов; с 20.10.2026
список заказов загружается постранично, как описано ниже. Финансовые
операции отбираются сервером копии до пагинации. Исходные renderer-компоненты,
формулы, права и внешние запреты сохранены.

Финансовые товарные отборы подключены в отдельном API копии: категории, типы,
номенклатура, артикул и восемь характеристик. `/finance/report` и
`/finance/filter-values` используют один отбор; варианты учитывают другие условия,
сохраняя альтернативы собственного поля. Используются исходные `app-filter-*`,
`FilterService` и `DataTable`. Строки отбираются после исходного финансового расчёта,
итоги складываются из выбранных строк. Налог и распределение начислений повторно
не рассчитываются; месячная себестоимость сохраняется. В недельном отчёте
подключены исходные категории, типы и общий итог. Подробности и воспроизводимые
проверки — в [sandbox_backend/README.md](sandbox_backend/README.md).
